# GitHub Portfolio Critic Agent

AI-агент (LangGraph, ReAct-патерн), що аналізує публічний GitHub-репозиторій
і дає структурований технічний фідбек — так, як це робить справжній технічний
рев'ювер перед прийняттям рішення про наймання.

## Чому це "справжній" AI-агент, а не просто виклик LLM

Замість одного фіксованого промта, агент **сам вирішує**, у якому порядку
викликати інструменти:
1. Спочатку дивиться загальну інформацію про репозиторій
2. Потім переглядає структуру файлів
3. Обов'язково перевіряє точку входу програми (main.py/app.py/bot.py)

Це і є суть **tool-calling агента**: LLM отримує набір інструментів з
описами, і сам, крок за кроком, вирішує, як їх використати.

## Продуктивність

Повний цикл аналізу виконується за **менше 5 секунд** — завдяки максимально
стислим описам інструментів (детальніше нижче, у розділі про 413-помилку)
та швидкій інфраструктурі inference Groq.

## Інструменти (tools) агента

- `get_repo_info` — загальна інформація (опис, мова, розмір)
- `list_repo_files` — структура файлів у репозиторії
- `get_file_content` — вміст конкретного файлу (для `.py`-файлів докстрінги
  автоматично видаляються перед відправкою до LLM, щоб зекономити
  токен-бюджет — див. нижче)

## Встановлення

```bash
pip install -r requirements.txt
```

Або через `pyproject.toml` (з dev-залежностями):
```bash
pip install -e ".[dev]"
```

Отримай безкоштовний ключ Groq на [console.groq.com](https://console.groq.com)
(без картки), створи `.env` на основі `.env.example`.

## Тестування

```bash
pytest -v
```

Покриття включає:
- `test_github_tools.py` — юніт-тести інструментів з mock'ами для мережі
  (404, ConnectionError, Timeout)
- `test_main.py` — тести `analyze_repo()`, включно з edge-case'ами:
  порожній `result["messages"]`, порожній/відсутній `content` у фінальному
  повідомленні (той самий баг, який реально виникав через замалий
  `max_tokens` у reasoning-моделі)

## CI (GitHub Actions)

При кожному push/pull request у `main` автоматично запускається lint
(`ruff`) та всі тести (`pytest`).

## Швидка перевірка (без LLM)

```bash
python test_tools_manually.py
```

## Запуск

```bash
python main.py
```

## Реальні проблеми, які довелось вирішити під час розробки

Ця секція — чесна історія розробки, з поясненням **кожної** причини, а не
тільки фінального рішення.

### 1. `create_react_agent() got an unexpected keyword argument 'prompt'`
Назва параметра для системного промта відрізняється між версіями
`langgraph`. **Рішення:** системний промт передається як звичайне
повідомлення в `messages`, а не через нестабільний kwarg.

### 2. `Recursion limit of 25 reached`
Агент "зациклювався", повторно викликаючи інструменти, не доходячи до
фінальної відповіді. **Рішення:** явний `max_tokens` для reasoning-моделі,
жорсткіші обмеження в системному промті ("виклич ОДИН раз"), запасний
`recursion_limit=50`.

### 3. Неповне покриття файлів під час аналізу
Агент сам обирав, які файли перевірити, і іноді пропускав ключовий
`main.py`. **Рішення:** зробили перевірку точки входу програми
обов'язковою частиною системного промта.

### 4. `413 Request too large` — ПЕРША причина (розмір файлу)
Спочатку здавалось, що причина — просто занадто довгий вміст файлу
(`main.py` з докстрінгами перевищував токен-бюджет). **Часткове рішення:**
написали `_strip_docstrings()` через модуль `ast`, що видаляє докстрінги
з Python-файлів перед відправкою до LLM (~30-65% економії розміру,
залежно від файлу).

### 5. `413 Request too large` — ДРУГА, справжня причина (token overhead tools)
Навіть після видалення докстрінгів з файлів, `413` **повторився**.
Справжня причина виявилась іншою: **докстрінги самих tool-функцій**
(`get_repo_info`, `list_repo_files`, `get_file_content`) використовуються
LangChain як опис інструмента для LLM — і цей опис **повторно
надсилається на кожному кроці** ReAct-циклу (агент "пам'ятає" список
доступних інструментів на кожному кроці рішення). Розлогі докстрінги
з повними Args/Returns/Raises помножувались на кількість кроків (3-4 рази),
створюючи основний token overhead.

**Рішення:** скоротили докстрінги трьох tool-функцій до 1-2 речень кожен
(orientовно 1857 символів економії **на кожен крок** агента).

**Цінний, задокументований інженерний trade-off:** докладні докстрінги, які
покращують читабельність коду для людей, одночасно є tool-описами для LLM
в агентних фреймворках — і їхній розмір множиться на кількість кроків
reasoning. Це прямий конфлікт між "якісною документацією за стандартами
код-рев'ю" та "токен-бюджетом" безкоштовних тірів API.

### 6. Порожня фінальна відповідь (IndexError/AttributeError у потенціалі)
Коли `max_tokens` виявлявся замалим для reasoning-моделі (яка витрачає
частину токенів на приховані роздуми), `result["messages"]` міг містити
повідомлення з порожнім `content`. Раніше код напряму робив
`result["messages"][-1].content`, що могло впасти з незрозумілою
помилкою при `messages == []`. **Рішення:** явна перевірка з зрозумілим
`RuntimeError`, покрита тестами (`test_main.py`) через mock агента з
різними "поламаними" сценаріями (порожній список, `content=""`,
`content=None`).

### 7. Плутанина "локальна версія vs версія на GitHub"
`get_file_content` завжди читає файл **з GitHub API**, а не з локального
диска — тому локальні зміни, які ще не запушені (`git push`), не
відображаються в аналізі, навіть якщо `python main.py` запускається
локально.

## Обмеження фідбеку самого агента (важливо!)

Під час кількох незалежних запусків агент **неодноразово** давав неточний
фідбек (стверджував, що файл "обривається", хоча насправді файл був
обрізаний навмисно через `MAX_FILE_CHARS`; стверджував відсутність
докстрінгів/CI/тестів, які реально були присутні в репозиторії, але
агенту не вистачило "бюджету" викликів `get_file_content`, щоб побачити
всі файли).

**Головний висновок:** якість аналізу ReAct-агента прямо обмежена (1)
кількістю файлів, які він фізично встиг прочитати в межах обмеженого
бюджету кроків/токенів, і (2) тим, наскільки повно він "прочитав" кожен
файл (обрізаний вміст = неповна картина). Це не помилка реалізації, а
**фундаментальне** обмеження tool-calling агентів на обмеженому бюджеті —
варто розуміти це, використовуючи подібні інструменти для реального
код-рев'ю, а не сприймати їхній висновок як остаточний аудит.

## Обмеження

- Працює тільки з **публічними** репозиторіями (без токена)
- GitHub API має ліміт 60 запитів/год без авторизації
- Groq безкоштовний тір має денний ліміт токенів (TPD), який виснажується
  при інтенсивному тестуванні протягом дня
- Фідбек агента не завжди точний (див. розділ вище) — інструмент для
  швидкого орієнтовного аналізу, а не заміна людського code review
